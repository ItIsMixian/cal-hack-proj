# 常驻公共小镇与邀请制私人小镇

Status: Proposed (2026-10-24). Not implemented as multiple functioning towns.

来源：[服务器与小镇讨论](../library/mirrorville-server-options.md)。用户讨论过共享区域、陌生人公共房间和私人邀请房间；“常驻公共小镇 + 邀请制私人小镇”及“一个分身同一时间只在一个小镇”是助手建议，尚未获用户选择。

对照基线：本地 main `8c6b381e08ee0b0b050b90d63a99113aac67053e`；本次未 fetch。

## 与 main 的差异与冲突

[仓库产品设计](../design/product-pipeline.md) 已提到 venue、teammates、invite-only old friends；私人房间这一概念并非本次新增。[0005](0005-mirror-room-privacy.md) 已有各房间的卡片可见性规则，但只有 venue 真正运行。

本提案的增量是选择常驻的公共／私人小镇组织方式，并明确真实成员与邀请机制，而不是把可见性 chips 当作房间实现。它与 [仓库原则](../core/repository-principles.md) 的“本周末不做 multi-world servers”存在范围冲突；本次不修改该原则或把多小镇排进本周末。

## 提案

- 将公共常驻小镇用于持续遇见新用户与逐步熟悉，私人小镇用于邀请既有朋友共同经历。
- 区分部署拓扑与社交空间：不预设每个逻辑小镇都要独立物理服务器。
- “单个分身同时只在一个小镇”保留为原型简化候选，未视为既定规则。
- 加入、退出、邀请和可见性需形成实际功能，才能称为多个可用小镇。

## 理由与替代方案

公共常驻空间强调重复相遇，私人空间强调维系已有关系。已讨论的替代方案包括单一共享世界、每次随机公共房间，以及维持当前单 venue 原型。各方案取舍保留在来源文档；尚未选定最终模式。

## 影响与待确认

- 小镇成员数量、邀请权限、加入／退出、分身跨镇行为与历史可见范围尚未决定。
- 需要协作者明确同意扩展范围和时间，才能调整现有“本周末不做多世界”的约束。
- [0007](0007-public-deployment.md) 的部署选择不构成本提案被接受或多房间已实现的证据。
