# Idea1 PRD：个性化活动管理工具生成器

版本：v0.1，原型需求初稿  
更新时间：2026-10-23  
原型交付日期：2026-10-25，具体交付时刻待定  
工作名称：Activity Helper（正式产品名称待定）  
目标终端：手机优先的活动专属网页／PWA，同时支持电脑浏览器

## 1. 产品定位

用户通过自然语言和共同编辑完成活动规划，平台根据活动方案生成专属网页／PWA，并通过该工具完成活动招募、共同决策、任务分工和进度追踪。

产品包含两个相连的工作空间：

1. **规划与生成空间**：整理活动目标、成员偏好和实际限制，辅助决策，生成和修改工具。
2. **活动专属工具**：提供活动需要的页面、字段、权限和流程，保存报名、投票、任务及进度数据，支持成员持续使用。

核心价值：减少组织者从策划到执行的协调成本，让好友能够共同决定活动并推动计划落地。

## 2. 已确认范围与待确认事项

### 2.1 用户已确认

| 项目 | 内容 |
| --- | --- |
| 场景 A | 大学社团等主办方策划活动，面向陌生人公开招募或定向邀请 |
| 场景 B | 好友约饭／出游，在共享编辑区域共同规划与决策 |
| AI 规划 | 推荐场地、饮食、活动类型等，并协助比较和完善方案 |
| 个性化 | 在获准情况下获取社交平台信息，归纳偏好并辅助推荐 |
| 生成形式 | 活动专属网页／PWA |
| 场景 A 的生成目标 | 活动宣传与报名工具，支持向选定社交媒体发布／分享 |
| 场景 B 的生成目标 | 按协商结果生成活动执行工具，让成员追踪和勾选推进事项 |
| 原型交付 | 2026-10-25 |

### 2.2 本稿提出的默认设计，尚非用户确认

- 通过 Messenger 等聊天中的共享链接进入同一个活动房间，原生群内入口作为后续接入项。
- 场景 A 由主办方确认方案、发布和重要变更；场景 B 由成员表达意见，发起人按房间设定的规则确认最终方案。
- 首版支持自然语言生成页面结构、活动内容、表单字段和任务规则；推荐用受控模块实现，以保证生成结果可用。
- 原型优先实现两种场景的完整流程。真实社交 API、真实社交媒体自动发布是否必须在截止日前接通，待确认。
- 时间、预算、成员意愿等缺失时提示补充，不以 AI 猜测替代用户确认。

## 3. 用户与角色

| 角色 | 核心需求 | 主要权限 |
| --- | --- | --- |
| 主办方／活动发起人 | 规划、生成工具、邀请、管理参与者、掌握进展 | 管理方案与工具版本；设置招募和决策规则；发布与结束活动 |
| 好友共同策划者 | 表达偏好、共同编辑、比较方案、投票 | 编辑开放的规划字段；提交自己的偏好和选票；参与执行 |
| 陌生参与者／受邀者 | 了解活动、申请或接受邀请、获取安排 | 查看可见内容；提交自己的报名资料；管理自己的报名与任务 |
| 协作者／志愿者 | 推进分工、报告进度 | 查看授权的执行信息；更新分配给自己的任务 |
| 未加入的访问者 | 判断是否参加 | 仅查看公开宣传内容，不查看成员私有信息 |

## 4. 两种核心使用场景

### 4.1 场景 A：社团主办方向陌生人招募

示例需求：主办方希望组织一次面向新成员的校园交流活动，需要确定形式、场地、餐饮、人数和执行分工。

流程：

1. 主办方输入活动目标、目标人群、日期范围、人数、预算及地点范围。
2. AI 补问关键信息，生成若干候选方案，说明场地、饮食、费用及待核实事项。
3. 主办方调整并确认方案，选择公开报名、定向邀请或两者结合。
4. AI 生成活动宣传页、报名／邀请流程和组织者管理区，供主办方预览与修改。
5. 主办方确认发布；获取链接、二维码与渠道文案，通过授权渠道发布或自行分享。
6. 陌生访问者报名或接受邀请；主办方按配置审核、查看名额和参与情况。
7. 成员在活动工具中查看最新安排、分工和待办；活动结束后留下反馈。

“活动申请”在本稿中拆为两类：主办方发送邀请；参与者提交报名申请。两类记录分别管理。

### 4.2 场景 B：好友共同决策与推进

示例需求：好友准备约饭或出游，尚未确定时间、目的地、预算和分工。

流程：

1. 发起人创建活动房间，将加入链接分享到已有好友群。
2. 好友进入共享编辑区域，提交本次时间、预算、出行范围与偏好。
3. 成员可分别连接受支持的社交账号，或主动提供内容；系统在允许的范围内整理兴趣线索，交由本人确认。
4. AI 汇总共同条件和冲突，推荐候选活动；成员补充方案、评价并投票。
5. AI 根据反馈解释取舍和未解决的问题，按房间规则由人确认最终活动。
6. AI 根据已确认内容生成活动专属网页／PWA，包括行程、任务、负责人、截止时间和完成检查。
7. 成员更新各自任务、报告阻碍、查看整体进展；方案变化时更新相应工具内容。

## 5. 活动生成器的输入与输出

### 5.1 输入

- 活动目标、场景类型、地点范围、人数及活动时间。
- 总预算／个人预算、交通、饮食、无障碍或其他必要条件。
- 成员本人确认的偏好；获准用于该用途的外部数据。
- 已选方案、投票结果、参与者角色和协商记录。
- 对工具的自然语言要求，例如“增加报名审核”“显示需要谁采购”“为行程增加集合检查”。

### 5.2 输出

| 输出层 | 生成内容 | 可验收结果 |
| --- | --- | --- |
| 活动方案 | 目标、时间地点、行程、预算、候选资源、未确认问题 | 用户能阅读、编辑和确认 |
| 工具配置 | 页面、导航、模块、字段、角色、状态与操作规则 | 不同活动产生相应的工具结构 |
| 运行工具 | 可打开的活动 URL、可填写的表单、投票、可更新的任务 | 多人使用同一个活动实例，数据持久保存 |
| 宣传内容 | 标题、简介、渠道文案、分享图素材或预览 | 主办方可预览、编辑并选择渠道 |

生成器需要支持内容和结构修改。例如：把“朋友聚餐”改为“周末出游”后，可新增行程、交通和携带物品模块；已有成员及有效任务记录应按更新规则保留。

## 7. 两种生成结果的页面结构

### 7.1 主办方活动工具

- **公开活动页**：活动介绍、适合人群、时间地点、费用说明、名额状态、报名入口。
- **报名／邀请页**：报名字段、邀请接受／拒绝、报名状态。
- **参与者活动页**：已确认安排、准备事项、通知与个人任务。
- **组织者管理区**：报名审核、参与名单、邀请记录、分工、整体进度和发布状态。

公开页不展示报名者联系方式、个人社交资料或内部组织任务。

### 7.2 好友活动工具

- **活动总览**：确认方案、成员状态、重要变更。
- **共同决策区**：偏好收集、候选方案、投票和决策记录。
- **行程与安排**：集合、交通、活动节点和地点信息。
- **任务与检查区**：个人任务、负责人、截止时间、完成／阻塞状态。

不同页面引用同一活动数据，避免宣传页、投票页和执行页各自保留互相冲突的时间地点。

## 8. AI 与数据使用要求

### 8.1 推荐原则

1. 优先遵守本次活动明确的必要条件，再比较偏好。
2. 将“从内容推测的兴趣”标为待本人确认；本次选择优先于历史线索。
3. 展示群体接受度、分歧及尚未回应的人，不用单一平均分掩盖必要条件冲突。
4. 推荐理由应可追溯到成员确认的条件或可核实的资源，不暴露成员未同意公开的原始内容。
5. AI 辅助比较、提出方案和生成工具；发布、最终确认及重要规则变化由有权用户执行。

### 8.2 外部数据与平台依赖

- 每位成员分别授权自己的账号；加入活动房间不会自动授权其社交信息。
- 每个连接器记录：可访问字段、权限范围、允许用途、有效期、最近同步时间及撤销状态。
- “技术上可读取”和“允许用于 AI 推荐”分别验证；尚未验证用途的数据不接入推荐服务。
- 成员可跳过账号连接，直接填写偏好；无权限、无数据、授权过期或断开时提供对应反馈。
- 外部账号令牌由后端保管，不显示给其他成员，不放入生成网页的公开配置。
- 场地、餐饮、营业时间、价格等来自接入的数据源或主办方输入；保存来源和更新时间。样本数据明确标注，未核实信息不作为实际订位承诺。

## 9. 协作、状态与变更规则

### 9.1 活动状态

草稿 → 规划中 → 待确认 → 已确认 → 执行中 → 已结束；另支持已取消。

工具发布状态独立管理：未生成 → 生成中 → 预览草稿 → 已发布 → 有未发布更新。生成失败不覆盖上一个可用版本。

### 9.2 关键规则

- 允许成员修改自己的偏好与选票；主办方不能冒充成员投票。
- 共同编辑时识别版本冲突，不静默覆盖他人的修改。
- 投票绑定候选方案版本；时间、地点或费用发生实质变化后，旧选票标为需重新确认。
- 最终确认时保存决策快照，展示参与人数、投票规则和未回应成员。
- 工具更新区分内容修改与流程结构修改；删除含报名／任务数据的模块前展示影响，并保留可恢复记录。
- 链接访问、身份和权限分别处理：知道公开活动链接不等于取得组织者权限。
- 活动取消后关闭新增报名和执行操作，向已加入成员展示取消状态。

| 对象 | 主要字段与用途 |
| --- | --- |
| User / Membership | 用户、活动内身份、角色、加入状态 |
| Activity | 模式、目标、约束、活动状态、可见性、当前方案版本 |
| Preference / Connection | 本人确认的偏好、来源、允许用途、授权状态 |
| Proposal / Vote / Decision | 候选版本、评价、个人选票、最终决策快照 |
| ToolSpec / ToolVersion | 页面、模块、字段、规则、版本、发布状态 |
| Invitation / Registration | 邀请对象、接受状态、报名字段、审核和名额状态 |
| Task / ProgressUpdate | 负责人、截止时间、完成状态、阻碍、变更记录 |
| Publication | 渠道、内容版本、人工／API 分享方式、实际发布结果 |

活动方案、工具配置和运行数据分别保存：重新生成页面不应重置参与者已经提交的记录。

## 11. 首版验收场景

### A. 社团活动完整演示

1. 主办方用自然语言创建活动并修改 AI 规划。
2. 生成宣传页、报名表和任务区，预览后发布。
3. 一位访问者通过公开页报名；另一位成员通过定向邀请加入。
4. 主办方查看名额和报名状态，完成一次审核或确认操作。
5. 志愿者完成一项任务，主办方看到对应进度变化。
6. 主办方修改活动时间；原有报名保留，参与者看到重要变更。
7. 宣传内容可复制分享；只有真实发布成功时才显示渠道“已发布”。

### B. 好友约饭／出游完整演示

1. 多个独立用户会话加入同一个活动房间并提交不同条件。
2. 演示从允许使用的数据或明确标注的样本归纳兴趣，并由成员修改确认。
3. AI 给出候选方案；成员提交不同选票，所有会话显示一致结果。
4. 至少演示一次条件冲突以及 AI 的协商建议。
5. 有权用户确认方案，生成具有相应页面、行程和任务的专属工具。
6. 不同成员完成各自任务，刷新后记录仍然存在。
7. 修改方案并更新工具，验证已有成员和完成记录未丢失。

### C. 通用验收

- 手机和电脑可完成加入、投票及任务检查，关键按钮和表单无明显遮挡。
- 生成中、生成失败、无数据、权限不足和成员未回应均有明确状态。
- 未获授权的用户不能访问他人的私有偏好或组织者管理接口。
- 演示数据、模拟连接和真实 API 结果明确区分，不将模拟能力计入真实接口验收。
- “生成成功”至少意味着工具可打开、关键操作可执行且数据可保存。

## 12. 成功指标

原型阶段先记录，不在没有基线时承诺提升幅度。

| 指标 | 定义 |
| --- | --- |
| 工具生成成功率 | 成功生成并通过关键操作检查的次数／生成尝试次数 |
| 首次可用工具耗时 | 从创建活动到首次发布可用工具的时间 |
| 好友决策完成率 | 达成明确最终方案的好友房间数／开始共同决策的房间数 |
| 决策耗时 | 从开始收集条件到确认方案的时间 |
| 报名转化 | 有效报名人数／公开活动页的独立访问人数 |
| 执行参与 | 至少完成一次有效任务更新的成员数／已加入成员数 |
| 计划落地 | 活动实际发生的情况，由主办方／成员反馈确认 |
